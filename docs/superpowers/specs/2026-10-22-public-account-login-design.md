# Public account login design

User confirmed Google, email verification code, Apple, and public self-registration without invite/share requirement. Extend existing users/JWT/refresh/RLS rather than replace accounts. Existing username/password login remains for old accounts; identities are bound after authenticating an existing account, not silently merged by matching names/email strings. New identity signup creates a private, non-admin user and no default subscriptions.

Email codes: six digits, ten-minute lifetime, five failed attempts, sixty-second resend interval and database-backed address/IP/global sending limits. Store only keyed hashes, consume atomically, never log code/address secrets; send outside transactions and invalidate failed delivery. A configured production sender and existing human-verification guard are prerequisites to availability. Verification and signup share one transaction so code cannot create multiple users.

Google/Apple: backend authorization-code flow with browser-bound single-use state and nonce; Google PKCE. Validate issuer/audience/expiry/signature/nonce/sub using trusted provider metadata. Apple web POST callback must work with secure SameSite=None cookies. Keep provider tokens server-side and exchange only a short-lived browser-bound one-use completion ticket for normal application login. No application JWT in URLs. Return destinations restricted to local allowed paths; continue existing capture/subscribe auth intentions.

Account identities are keyed by provider+subject. Authenticated binding uses server-bound user ID; uniqueness prevents identity takeover. Email relay claims are not proof of equivalence to another provider identity. New provider configurations must not enable unsafe fallback accounts. Unconfigured providers are omitted with clear readiness state; do not claim live login without real provider account and delivery verification.

Production requirements: verified outbound sender/SMTP or transactional-mail API; Google OAuth client and exact callback; Apple Developer configuration, primary App ID, web Services ID, signing key and callback. Credentials are entered through secure local/server configuration, never chat or source control. No paid signup/provider purchase or external test mail is sent before destination/provider is supplied. Public registration switch is separate from credential readiness, and new verified auth methods do not require invites.
