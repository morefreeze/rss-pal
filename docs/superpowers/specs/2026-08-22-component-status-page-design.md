# RSS Pal 组件状态页设计

## 目标

升级现有公开 `/status` 页面，使其按组件展示当前状态和最近 72 小时可用情况。页面参考常见公共状态页的结构，保持无需登录访问，同时不暴露容器、数据库或内网地址。

首版展示以下六项：

1. Frontend
2. API
3. Worker
4. RSSHub
5. Status Monitor
6. 公网入口

PostgreSQL 和 YouTube POT 不在首版页面中展示。

## 状态模型

组件健康状态只有两档：

- `up`：正常
- `down`：故障

历史不足时允许出现灰色“无数据”状态条。无数据只表达尚未采样，不属于第三种健康状态，也不参与可用率计算。

整体状态规则：

- 所有组件当前均为 `up`：显示“所有系统运行正常”。
- 任一组件当前为 `down`：显示“部分系统故障”。

## 页面设计

### 页面结构

页面顶部展示：

- `RSS Pal Status` 标题
- 最后更新时间
- 每 60 秒刷新提示
- 整体状态横幅

组件列表中每个组件独占一行，包含：

- 组件名称
- 当前状态
- 最近 72 小时的 72 根小时状态条
- 最近 72 小时可用率
- “72 小时前”到“现在”的时间轴

桌面端与移动端保持相同的信息结构。移动端压缩状态条间距，不横向裁掉组件名称、当前状态或可用率。

### 小时状态条

每根状态条表示一个自然小时：

- 该小时有采样且全部成功：绿色
- 该小时有任一失败采样：红色
- 该小时没有采样：灰色

72 小时可用率按该时间窗口内的实际采样计算：

`成功采样数 / 有效采样总数 × 100%`

无数据时段不进入分母。

### 小时明细

桌面端鼠标 Hover 状态条、移动端点击状态条时展示 Tooltip，包含：

- 小时时间范围
- 正常或故障
- 该小时可用率
- 成功次数 / 总检查次数
- 平均延迟
- 若发生故障，展示最近一次错误原因和发生时间

错误原因必须经过截断和转义，不展示内部 URL、凭据、SQL、堆栈或容器地址。

## 探测架构

继续使用独立 `status-monitor` 服务。它每 60 秒并发探测各组件，并将每次采样写入现有 SQLite 数据库。单个组件探测超时为 10 秒；某一组件失败不得阻塞其他组件采样。

### Frontend

Status Monitor 请求 Docker 内网中的 Frontend 首页。HTTP 2xx 或 3xx 视为正常；连接错误、超时或其他状态码视为故障。

### API

Status Monitor 请求 API 的 `/api/health`。仅当响应为 HTTP 200、JSON 可解析且 `status` 为 `ok` 时视为正常。

### Worker

新增持久化服务心跳，包含组件名和最后心跳时间。Worker 启动后立即写入一次心跳，并由独立定时器每 60 秒更新 `worker` 心跳，避免耗时超过 3 分钟的正常抓取循环被误判为故障。

API 提供 `GET /api/internal/health/worker` 只读接口。最后心跳距当前时间不超过 3 分钟时为正常，超过 3 分钟或读取失败时为故障。Status Monitor 通过 Docker 内网直接请求 API；Nginx 对该路径返回 404，避免公网访问。

Worker 的其他独立 goroutine 不单独建组件；首版 Worker 状态代表主抓取循环仍在持续运行。

### RSSHub

Status Monitor 请求 RSSHub 内网 HTTP 服务的轻量端点。HTTP 2xx 或 3xx 视为正常；连接错误、超时或其他状态码视为故障。不得使用会触发真实订阅抓取的重型路由作为健康检查。

### Status Monitor

Status Monitor 记录每轮监控循环完成时间。如果最近一次循环在两个采样周期内完成，则自身状态为正常；超过 120 秒未完成则为故障。

自身状态不通过递归 HTTP 请求判断，避免 `/status` 对自身形成循环依赖。

### 公网入口

Status Monitor 请求 `https://rss.morefreeze.top/api/health`，验证 DNS、TLS、外部 Nginx 和 API 整条公网路径。仅当响应为 HTTP 200、JSON 可解析且 `status` 为 `ok` 时视为正常。

公网探测 URL 由配置提供，API 响应和 Tooltip 不返回该 URL。

## 数据结构与接口

### SQLite 采样

扩展现有 `checks` 表的 `source` 使用范围，使其保存六个固定组件标识。继续保存：

- 采样时间
- 组件标识
- `up` / `down`
- HTTP 状态码（若适用）
- 延迟毫秒数（若适用）
- 已清洗、截断的错误摘要

保留至少 7 天原始采样，页面接口只返回最近 72 小时所需数据。

现有 `local` 和 `domain` 历史不迁移到新组件名，以免把旧的整体探测误称为具体组件。部署后新组件从零开始积累数据，缺失小时显示灰色。

### Worker 心跳

新增数据库迁移，创建单行可更新的服务心跳结构。更新操作必须使用数据库时间，避免 Worker 容器与 API 容器时钟差异。

心跳表只承担进程活跃性判断，不保存任务日志或业务明细。

### `/api/status`

保留现有公开 `GET /api/status`，调整响应为组件化结构：

- 总体当前状态
- 服务端生成时间
- 采样间隔
- 六个固定组件
- 每个组件的当前状态、72 小时可用率和 72 个小时桶
- 每个小时桶的 Tooltip 明细字段

前端页面只消费聚合后的小时桶，不在浏览器中下载或重新聚合 72 小时原始采样。

## 刷新、失败与降级

- 后台每 60 秒完成一轮采样。
- 页面每 60 秒请求一次 `/api/status`。
- 页面首次加载立即请求数据，不等待首个定时器周期。
- `/api/status` 刷新失败时，保留上一次成功渲染的数据，并显示“数据暂时无法刷新”。
- 单个组件探测失败只影响该组件。
- SQLite 读取失败时，接口返回明确的失败响应，不构造虚假的全绿结果。
- Tooltip 中不可安全公开的原始错误统一映射为简短错误类别，例如“连接超时”“连接失败”“响应格式异常”。

## 安全与兼容性

- `/status` 和 `GET /api/status` 保持公开，无需登录。
- Worker 健康探测固定使用 `GET /api/internal/health/worker`。Nginx 在通用 `/api` 代理规则之前对该精确路径返回 404；Status Monitor 只通过 Docker 内网访问 API。
- 不挂载 Docker socket。
- 不向浏览器返回数据库地址、容器名、内网 URL、凭据、SQL 或堆栈。
- 保留 Nginx 中 `/status` 和 `/api/status` 的既有路由，已有书签继续有效。

## 测试

### 单元测试

- 六个组件的正常、超时、连接失败和非预期响应。
- API 必须校验 HTTP 200、JSON 和 `status=ok`。
- Worker 心跳临界值：未过期、恰好过期、已过期和读取失败。
- 72 个小时桶的时间边界、红绿灰聚合及排序。
- 可用率忽略无数据时段。
- Tooltip 的成功次数、总次数、平均延迟和最近错误。
- 错误摘要的截断、转义和敏感信息清洗。
- 整体状态汇总。
- SQLite 读取失败时不得返回全绿。

### 页面测试

- 六个组件均渲染当前状态、72 根状态条和可用率。
- 桌面端 Hover 展示小时明细。
- 移动端点击展示小时明细。
- 页面首次加载立即请求，之后每 60 秒刷新。
- 刷新失败时保留旧数据并显示提示。
- 桌面端和窄屏布局不溢出关键内容。

### Compose 与验收

- 在 Compose 网络中验证 Status Monitor 能访问 Frontend、API 和 RSSHub。
- 验证 Worker 心跳会持续更新，停止 Worker 后 3 分钟内转为故障。
- 验证 Status Monitor 循环停滞超过 120 秒后自身显示故障。
- 验证公网入口探测使用真实公网路径。
- 验证 `/status` 无需登录即可访问。
- 验证页面每分钟刷新，6 个组件具有当前状态和最近 72 小时视图。
- 验证页面响应不包含内部地址或敏感错误信息。

## 不在本次范围

- PostgreSQL 和 YouTube POT 的独立组件行
- 正常、故障以外的性能下降或部分故障等级
- 订阅状态更新或通知推送
- 故障事件的人工维护、公告和复盘页面
- 72 小时以外的历史查询页面
